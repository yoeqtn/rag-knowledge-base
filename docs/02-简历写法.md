# 简历怎么写这个项目

> 原则：**每一条都要能被追问三层**。写不出来的技术，不要写进简历。

---

## 一、项目标题

```
企业知识库 RAG 问答系统（个人项目）    2026.12 – 2027.01
Python / FastAPI / PostgreSQL + pgvector / Docker
```

标题只放**你真用过、能讲清楚**的技术。没用的不要写。
如果有人问你"为什么不用 LangChain"——这个项目刻意手写，答案见面试文档，反而是加分项。

---

## 二、三个版本，按你的实验数据选

### 版本 A：保守版（还没做对比实验时用）

```
· 独立设计并实现企业文档问答服务，支持 PDF/Word/Markdown 解析、父子块切分与向量化入库
· 采用 BM25 + 向量双路召回并以 RRF 融合，命中子块后回溯父块补全上下文
· 实现 SSE 流式输出与引用溯源，回答可定位到具体文档与原文片段
· Docker Compose 部署 PostgreSQL + pgvector（HNSW 索引），pytest 覆盖核心链路
```

优点：全部可验证，不会被问穿。
缺点：没有数字，在筛简历时不够亮。

---

### 版本 B：标准版（做完 3 个对比实验后，**推荐用这个**）

```
· 面向 11 篇企业制度文档构建知识库；在同一块长下做对照实验，块长 200 时父子块切分
  将检索精度从 49.0% 提升至 74.5%，块长 500 时两者持平，据此定位收益来源是
  小粒度子块而非父块本身
· 实现 BM25 + 向量双路召回与 RRF 融合；对照实验显示纯 BM25 在无词面重叠的问题上
  漏召回（16/17），融合后 Recall@3 达 100%、MRR 1.0，代价是延迟从 8ms 升到 60ms
· 基于 SSE 实现流式回答与引用溯源，回答可定位到具体文档块与原文片段
· Docker Compose + pgvector（HNSW 索引）部署，pytest 覆盖 29 个用例
```

> 上面的数字来自 2026-11-06 的实测（11 篇文档、17 条口语化问题、top_k=3），
> 脚本是 `scripts/experiment_chunking.py`，结果在 `results/chunking-hard.md`。
> 语料规模仍然偏小，扩到 50 篇以上后应重跑并更新。

**为什么这条写得比"Recall 提升 X%"好**：它给出了对照组和机制解释。
面试官听到"块长 500 时两者持平"会知道你做过消融实验，而不是碰巧跑出一个好数字。

---

### 版本 C：进取版（只在你确实做了额外工程时才用）

```
· 从零实现 RAG 检索链路（解析 / 切块 / 双路召回 / RRF / rerank / 父块回溯），未依赖 LangChain，
  可清晰解释每一层的取舍与代价
· 设计 Store 抽象层，同一套业务代码可在内存实现（测试，毫秒级）与 pgvector 实现（生产）之间切换
· 建立 120 题评测集，覆盖同义改写、多跳与干扰文档，Recall@5 稳定在 0.88，MRR 0.79
· 接入语义缓存与 token 计费，单次问答平均成本 ¥0.0009，缓存命中率 31%
```

版本 C 的前提是：你真的建了 120 题评测集。**没有就别写。**

## 三、每条 bullet 的写法拆解

一条合格的项目描述 = **做了什么 + 用了什么技术 + 达成了什么可验证的结果**。

| 差 | 好 |
|---|---|
| 使用 FastAPI 搭建后端服务 | 实现文档上传、问答、统计 7 个 REST 接口，写操作走 API Key 鉴权，按租户隔离数据 |
| 使用了 RAG 技术 | 实现 BM25 + 向量双路召回与 RRF 融合，相比纯向量 MRR 提升 23% |
| 支持引用 | 回答中的 [n] 解析后映射回文件名与原文片段，越界编号直接丢弃 |
| 部署上线 | Docker Compose 部署 API + PostgreSQL + pgvector，建 HNSW 索引，单机支撑 1.2 万文档块检索 P95 < 80ms |

注意最后一条：**"P95 < 80ms" 这种数字必须是自己压测出来的**。可以写，但要能解释怎么测的（比如用 `hey` 或 `locust` 跑 100 并发）。

## 四、数字从哪来（对照表）

| 简历里的话 | 用哪个实验产出 |
|---|---|
| Recall@5 从 X 提升到 Y | `scripts/evaluate.py --offline`，分别跑 vector-only 和 hybrid |
| MRR 提升 X% | 同上，看 MRR 指标 |
| rerank 后 top-1 提升 X 个百分点 | `RERANK_ENABLED=true` 前后各跑一次 |
| 平均延迟 X ms | `--offline` 输出里的 latency，或 `/api/stats` |
| 单次成本 ¥X | `/api/stats` 的 `cost_cny / queries` |
| 缓存命中率 X% | 先用同一批问题跑两遍，再看 `cache_hit_rate` |
| 覆盖 N 个测试用例 | `pytest` 的输出数字 |

**流程**：改配置 → 跑评测 → 记表格 → 写简历。不要反过来。

## 五、技能栏怎么写

按"熟练度分层"，别堆砌关键词：

```
语言：Python（熟练）、SQL、JavaScript（了解）
后端：FastAPI、SQLAlchemy、Pydantic、RESTful API、SSE、JWT
数据：PostgreSQL、pgvector、BM25、Redis（了解）
AI  ：RAG、Embedding、Rerank、Prompt Engineering、OpenAI 兼容 API 接入
工程：Docker、Git、pytest、Linux 常用命令
```

三条纪律：

1. **"了解"就写"了解"**，别全都写"熟悉"。面试官专挑你写"精通"的问。
2. **不写没碰过的**。写了 Redis 就会被问缓存穿透、过期策略。
3. **不写"精通"**。校招简历写精通，等于邀请对方往死里问。

---

## 六、雷区清单

| 雷区 | 为什么危险 |
|---|---|
| 写"使用 LangChain 搭建 RAG" | 你没用；而且一旦被问 LangChain 的 `Retriever` 生命周期就露馅 |
| 写"准确率 100%" | 一眼假，直接扣分 |
| 写"服务 1000+ 用户" | 会被问怎么推广的、留存多少、服务器多大 |
| 把教程项目原样写上去 | 面试官见过几百份一模一样的 |
| 只写技术名词不写结果 | "使用了向量数据库" 等于没说 |
| 项目时间写成 3 天 | 显得没有深度；至少写 2~3 周 |

## 七、简历写完后自检

对着简历，逐条问自己：

- [ ] 这条里的每个技术名词，我能在 30 秒内解释它是什么、为什么用它吗？
- [ ] 这条里的每个数字，我能说出是怎么测出来的吗？
- [ ] 如果面试官说"你现在现场改一下"，我知道改哪个文件吗？
- [ ] 如果面试官说"这个方案有什么缺点"，我答得出来吗？

四个问题有一个答不上来，就把那条改弱一点，或者删掉。

> 一份能被追问三层还站得住的简历，比一份堆满名词的简历值钱得多。
